FULL DELEGATION
核心结论 · BLUF

内部高手的进阶，几乎全部发生在三个普通用户看不到的层面：心智模型、上下文工程、智能体编排——而不是"咒语式"的 Prompt 技巧。

① 心智模型先变，效率才会变。普通人追求"一次问对"；内部人默认"迭代 + 并行 + 管理"。最贵的认知升级是：把自己从"向 AI 提问的人"，重新定位成"一群 Claude 的管理者与审阅者"，并据此重排工作流。一位研究员的原话是，与其要一台更快的车，不如拥有一千匹马去同时试很多想法。[A1]

② 上下文 = 有限的"注意力预算"，必须像工程一样经营。Anthropic 已把焦点从 "Prompt Engineering" 升级为 "Context Engineering（上下文工程）"：找到"信号最高、数量最少"的那批 token。会变长的对话会"注意力衰减"（context rot），所以高手主动做压缩、外部笔记、子代理隔离，而不是把所有东西塞进一个窗口。[A2]

③ Agentic 用法（Claude Code / Cowork）才是内外差距最大的地方。外部人多把它当"写代码工具"；内部的律师用它搭电话转接系统、市场团队几秒生成上百条广告、数据科学家不懂 JS 也能做可视化。关键招式如规划模式、子代理互相挑刺、stop hook 强制收尾、并行迁移，外部几乎无人系统使用。[A3][S1]

④ 但要去掉幻觉。同样来自内部：Claude Code 首次全自动尝试只有约 1/3 成功率；让审阅子代理"找问题"它一定会找出问题，盲目照改会过度工程化；在熟悉的大型代码库里，开发者常高估 AI 带来的提速。把方法用对，远比用得多重要。[S3][A1]

§01

内部人与普通人的根本差异：心智模型

MENTAL MODELS · 工具相同，假设不同，结果天差地别

同样一个 Claude，普通人和内部高手用出来的差距，90% 来自使用前的假设，而不是指令本身。下面四组心智模型，是内部人默认、外部人陌生的"操作系统"。

MODEL 01

从"问答"到"管理一群 Claude"

内部工程师把自己重新定义为 "AI 智能体的管理者"——有人常态化同时挂着多个实例，把工作重心从"亲手写"转向"为 1 个、5 个甚至 100 个 Claude 的产出负责"。约 70% 的角色已从"写新代码"变成"审阅与修订"。

外部人不知道把任务当"可并行的工单流"派发，而不是排队等一个回答。
MODEL 02

一千匹马，而不是一台快车

不要把"更强的模型"想成"更快的同一个实例"。高手会并行起多个 Claude，各自走不同解法，再挑最好的——广度本身带来创造力。一个想法不确定时，就同时试五种，而非纠结选哪一种。

怎么落地多开几个对话/会话分头试不同 prompt 或方案，几分钟后比对结果。
MODEL 03

"合适的高度"：别太死也别太空

给 AI 的指令要落在 Goldilocks 区间：一端是把复杂逻辑写死（脆弱、难维护），另一端是含糊的高层口号（模型抓不到信号）。正确做法是给足"强启发式"，但留出让模型自己发挥的空间。

反直觉用"深入思考一下这个问题"往往比一步步硬性规定，效果更好。
MODEL 04

选对模型：你知道要什么吗？

Cowork 负责人的启发式：问题清晰、范围明确 → 用 Sonnet；连自己想要什么都说不清、需要 AI 帮你厘清 → 用 Opus。"给我画个带户型的平面图"是 Sonnet 活；"帮我想清楚怎么安排我的人生"是 Opus 活。

对应你的栈日常驱动用快/省的模型，战略性、开放性问题才上最强模型——和你的路由策略一致。
"合适的高度" · 系统指令的两种失败模式FIG.01 / SOURCE A2
读法：多数人要么把规则写死（左），要么只丢一句"帮我写好点"（右）。内部经验是瞄准中间——清楚到能指挥行为，又灵活到让模型用自己的推理补全。模型越强，越往右松手。

"把超强模型想成单一实例，就像追求一台更快的车。但拥有一千匹马，能让你同时去试很多想法。"

— Anthropic 一位研究员，转引自 [A1]
§02

对话层：官方推荐、却少有人真用的进阶技巧

PROMPTING · 不是咒语，是结构化沟通

这些技巧 Anthropic 官方文档都写了，但外部用户的实际使用率极低。它们的共同点：把"随口聊"升级为"有结构、可预期"的沟通。

技巧 A

用 XML / 标签切分上下文

Claude 是专门训练过识别 XML 结构的。把指令、数据、示例、输出要求用 <instructions> <data> 等标签分区，能显著减少"它把资料当指令、把例子当正文"的混淆。标签名没有标准，看得懂即可。

适用长资料 + 多类型内容 + 需要稳定输出格式时，收益最大。
技巧 B

预填回答（Prefill）锁定格式

在 API 里可以替模型"开个头"——直接写下回答的前几个字（如 <thinking> 或 {），它会顺着往下接。这是强制跳过寒暄、锁定 JSON / 特定格式最有效的手段之一。

对你的栈做结构化抽取、批量数据管线时，prefill 比反复叮嘱"只输出 JSON"更可靠。
技巧 C

Extended Thinking 取代手写 CoT

过去要手动写"一步步想"，现在扩展思考已自动化结构化推理，官方认为通常优于手写思维链。诀窍：从最小思考预算起步、逐步加码；思考过程用英文、最终答案可用中文；并检查思考是否跑偏。

反直觉给"深入思考"这种高层指令，常比详细规定步骤更好——让它自己惊艳你。
技巧 D

少而精的"标杆示例"，而非堆边界

很多人把所有 edge case 罗列进 prompt，官方明确不推荐。正确做法是给几个多样、典型、规范的示例——对模型而言，"示例就是胜过千言的图片"。

常见错误用 20 条特例去描述规则，不如 3 条好示例画出"对的样子"。
技巧 E

解释"为什么"，给约束动机

新一代模型遵循指令空前精确。告诉它约束背后的原因（如"这段会被语音朗读，所以不要用省略号"），比单纯下命令效果好得多——它能据此推广到你没明说的同类情况。

动词要硬想让它直接动手就说"做这些修改"，而不是"你能不能建议一些改动"。
技巧 F

让 Claude 写给 Claude 的 Prompt

把"写好提示词"本身交给模型：用官方的 Prompt Improver，或直接让 Claude 基于你的目标起草、再迭代。先建立"成功长什么样 + 怎么测"，再让它优化——这就是"元提示"。

省时与其自己憋完美 prompt，不如让它产出几版你来挑、来改。

把抽象变具体——同一个需求，两种写法的差距：

✕ 普通写法 · 模糊
# 一句话甩过去
帮我分析一下这份用户调研，
写个总结。
✓ 进阶写法 · 结构化
<role>资深用户研究员</role>
<data>{粘贴调研原文}</data>
<task>
深入思考后，按"结论先行"
输出：1)3条关键发现(各配数据)
2)最强的反对解读 3)2个待验证项
# 给动机：这份要给 CEO 拍板用
</task>
<format>中文·不超过400字</format>
§03

Agentic 层：内部差距最大的"暗招"

CLAUDE CODE / COWORK · 不只是写代码，是自动化整条工作流

这是内外差距最悬殊的一层。外部人把 Claude Code 当 IDE 插件；内部人把它当"能自己动手的通用智能体"——而且非工程岗用得同样狠。

先看内部到底拿它干什么（多数会让你意外）：法务团队搭了"电话树"系统帮同事找对的律师；增长市场团队用两个专用子代理，几分钟生成上百条符合严格字数限制（标题 30 字符、描述 90 字符）的广告变体，还做了 Figma 插件一次批量产出 100 个版本；数据基础设施团队在 K8s 集群宕机时，把仪表盘截图喂给它，被一步步引导到"Pod IP 耗尽"的根因并拿到修复命令，绕过了网络专家；不懂代码的财务同事，只用自然语言描述"查这个看板→跑这些查询→产出 Excel"，它就把整条流程跑完。[A3]

招式 01

别想"一把梭"——先开规划模式

新手以为 Claude Code 能 one-shot 一切，并不现实。复杂任务先切到 Plan Mode，让它把步骤列清、与你对齐方案，再动手写——成功率能翻一到两倍。

来自创造者Boris Cherny：复杂任务先规划、再执行，是最高 ROI 的一步。
招式 02

让子代理"互相挑刺"

代码评审命令一次并行起多个子代理：一个查风格、一个翻项目历史、一个抓 bug。第一轮会有真问题也有误报，于是再起 5 个专门"挑前面结论的毛病"——最后只留真问题，几乎没有误报。

精髓对抗式多代理 = 用一组 AI 去校验另一组 AI 的结论。
招式 03

Stop Hook：不干完不准停

设一个"收尾钩子"：当它想把控制权交还给你时，自动跑测试套件，只要有测试没过，就回去让它继续修、继续测。"你可以让模型一直跑到事情真正做完为止。"

本质把"验收标准"写成自动闸门，逼模型自洽闭环。
招式 04

团队共享 settings.json

把配置文件放进代码库：预批准常用命令（让它不再为日常操作反复请示）、拉黑危险操作（绝不可碰的文件）。全队继承同一套合理默认，而不是各配各的。

类比你的栈等同于给 Agent 写一份团队级的"权限+规范"基线。
招式 05

并行子代理跑"无聊的迁移"

大规模迁移（换测试框架、框架升级）这类易验证、纯体力的活，让主代理先列 to-do，再派子代理并行处理。有工程师每月在这类迁移上花掉 $1,000+ 的额度——因为它真的省人。

判据输出容易自动验证的任务，最适合放手并行。
招式 06

自定义斜杠命令 + MCP 管访问

把高频工作流封装成 /斜杠命令（安全团队贡献了整个仓库一半的自定义命令）。涉及敏感数据时，用 MCP server 而非直接 CLI，以便对"Claude 能访问什么"做日志与权限控制。

沉淀把"重复做的事"固化成命令/技能，是从"会用"到"高效"的分水岭。
自主性增长 · Claude Code 越来越"敢放手"FIG.02 / SOURCE A1
含义："自主性"在半年内显著提升——这意味着你越早建立"派发 + 验收"的工作流，复利越大。但同一份研究也提醒：能完全无监督交付的工作仍只占 0–20%。
§04

上下文工程：把"注意力"当成预算来经营

CONTEXT ENGINEERING · 从"写好提示"到"管好整个上下文状态"

这是 Anthropic 内部最新、也最被外部低估的范式升级。一句话：找到信号最高、数量最少的那批 token，因为模型的注意力是会被耗尽的有限资源。

为什么重要：研究显示存在 "context rot（上下文衰减）"——上下文里的 token 越多，模型从中准确回忆信息的能力越下降。这不是断崖，而是一条逐渐变陡的下坡：模型在长上下文里依然能干，但检索精度与长程推理会打折。所以"把所有资料一股脑塞进窗口"是反模式。[A2]

上下文衰减 · 注意力是会耗尽的预算（示意）FIG.03 / 概念图 · SOURCE A2
示意而非精确测量。Anthropic 强调这是"性能梯度"而非硬断崖。实践结论一致：上下文要"信息充分但尽量紧凑"，而不是越长越好。

内部用来对抗衰减的三件套（长任务必备）：

武器 01

压缩（Compaction）

对话快到窗口上限时，把历史摘要成高保真的精华，再开一个新窗口续上。Claude Code 就是这么做的：保留架构决策、未解 bug、关键实现，丢掉冗余的工具输出，再带上最近访问的 5 个文件继续。

最轻量的一招清掉深层历史里早已用过的工具调用结果——它不需要再看一遍原始返回。
武器 02

结构化笔记（外部记忆）

让 Agent 把笔记写到上下文窗口之外的文件（如 NOTES.md、to-do 列表），需要时再读回来。"Claude 玩宝可梦"靠这招在上千步里维持目标、地图与战术记忆，窗口重置后读回笔记继续打。

对你的栈这正是 QMD / SOUL.md / USER.md 这类外部记忆文件的底层逻辑。
武器 03

子代理架构（隔离上下文）

不让一个 Agent 扛全程，而是派专门子代理处理聚焦子任务、各自用干净窗口。子代理可能烧掉几万 token 深挖，但只回传 1,000–2,000 token 的提炼结论。主代理负责统筹与综合。

研究实测多代理架构在复杂研究任务上显著优于单代理。

还有一条心法叫"按需取用"（just-in-time）：不要预先把所有数据灌进去，而是保留轻量指针（文件路径、查询、链接），运行时用工具动态加载——就像人类不背下整本书，而是靠文件系统、收件箱、书签按需检索。Claude Code 对大数据库就这么做：写定向查询、存结果、用 head/tail 分析，从不把整个数据对象塞进上下文。[A2]

§05

研究员的日常习惯：什么交给 AI，什么留给自己

DELEGATION · 高手的判断力，藏在"不用 AI"的那部分

内部研究最有价值的发现之一：高手不是"什么都丢给 AI"，而是发展出一套清晰的委派直觉。用错地方，反而更慢（外部 METR 研究也证实：在熟悉的大代码库里，开发者常高估 AI 提速）。

该交给 AI 的任务，符合这几条特征——

✓
低上下文 + 低复杂度

你了解不多、但整体也不难的事（如不熟的 Git/Linux 操作、不熟语言的小脚本）。

✓
容易验证

"验证成本 ≪ 创造成本"时最香——一眼能看出对错，就放心交。

✓
定义清晰 / 自包含

子模块与系统其余部分充分解耦时，让它先试一版。

✓
质量要求不极端

一次性的调试代码、探索性研究代码，直接交。

✓
重复 / 无聊

"我越想亲手做的任务，越不会用 AI"——阻力越大、越该开个对话起步。

✓
"说"比"做"快

但反过来：预计 10 分钟内能搞定、或交代清楚成本太高（cold start）的，自己做更快。

放手交给 AI

新功能开发、调试、跨语言改写、补测试、写文档、做可视化、踩不熟的领域、"补全你记忆/熟悉度空白"的查证。一位后端工程师靠迭代让 Claude 做出了"自己绝对做不出、还按时交付"的复杂 UI，设计师惊呼"这是你做的？"——"不，是 Claude 做的，我只是给了提示。"

留给自己

高层与战略思考、需要组织背景与"品味"的设计决策。研究数据里，设计/规划正是生产力提升最小的一类。一位安全工程师警告：模型曾给出"危险地聪明"的方案——只有有经验的人才看得出它有问题。这条边界在随模型变强而不断重新协商。

三个可直接抄的研究员习惯：
① 并行探索：同一问题同时挂多个实例走不同解法，再挑最优——把"试错"并行化。
② 把它当"加速学习器"：踩新领域时让 Claude 当专家、给你选项与该研究的方向；一位员工说"学东西/变得有效的速度彻底变了，天花板像是被打碎了"。
③ 刻意保持手感：正因为依赖会让技能退化（"监督悖论"——监督 AI 恰恰需要那些可能退化的技能），有人会偶尔故意不让 Claude 做它明明能做的题，以保持锋利。

§06

反方视角：哪些"高级技巧"其实被高估

THE OTHER SIDE · 用对，比用多重要

结论再清晰，也要给最强的反对意见。以下几条同样来自内部一手观察——它们能帮你避开把方法用成玄学的坑。

CAVEAT 01

"全自动一次成功"是幻觉

内部 RL 工程团队的数据：Claude Code 首次全自动尝试只有约 1/3 成功率。把它当"按一下就交付"会反复翻车——真正的工作流是"派发 → 检查 → 迭代"。

CAVEAT 02

"让它找问题"必然找到问题

你让审阅子代理"挑毛病"，它一定会报一堆——即使代码本就没问题。盲目照单全改会导致过度工程化：多余抽象、防御式代码、为不可能的情况写测试。要明确只修"影响正确性/需求"的，其余当可选。

CAVEAT 03

在你熟悉的领域，AI 常被高估

外部 METR 研究：经验丰富的开发者在高度熟悉的代码库里，高估了 AI 带来的提速。内部委派标准恰好印证——熟悉、复杂、隐性知识多的场景，自己做可能更快。

CAVEAT 04

"厨房水槽"式会话会拖垮质量

官方点名的常见错误：一个会话里先问 A，又插一个无关的 B，再回去做 A。上下文被污染，输出变差。正确做法是一个会话一个聚焦目标，新任务就开新窗口。

CAVEAT 05

格式技巧的边际收益在递减

XML 标签、精确分区在复杂、多类型内容时仍有用，但官方也直言：随着模型变强，提示词的精确格式正变得不那么关键。别把精力过度花在"咒语调参"上，重心应是上下文与任务设计。

CAVEAT 06

技能退化是真实代价

"产出太容易，就越来越难静下心真正学会一件事。"过度委派会让深层技能与"顺带学到的"系统理解一起流失——而这恰恰是你日后审阅 AI 所依赖的能力。这是效率的隐性账单。

§07

决策含义 · 给你的采纳优先级

FOR 磊哥 / 开开华彩 · 按 ROI 与上手成本排序

结合你已有的 AI 栈（OpenClaw / 多模型路由 / QMD 记忆 / 飞书 Agent）与业务场景（开开华彩在线 + 项目二线下获客），下面是从高 ROI / 低成本到战略性投入的落地顺序。

技巧矩阵 · 能力提升 × 上手成本FIG.04 / 综合判断
读法：左上角"立刻就做"是认知/习惯类，几乎零搭建成本、收益最大；右上角是需要你投入搭建（但对项目二自动化潜力巨大）的工程化方向；右下角的"咒语调参"性价比最低，别陷进去。
1本周
把"委派直觉 + 规划模式"变成默认动作零成本·最高ROI

用 §05 的六条判据筛任务：易验证、自包含、重复无聊的先交，战略与"品味"留给自己；复杂任务一律先让模型出方案再执行。这一条带来的提升，超过任何 Prompt 技巧。

2本周
升级你的记忆文件为"上下文工程"贴合现有栈

你已有 SOUL.md / USER.md / QMD——按 §04 原则审一遍：是不是"信号最高、数量最少"？把长资料改成"按需取用"（指针 + 动态加载），给长任务加结构化笔记（NOTES.md）与压缩策略，对抗上下文衰减。

3两周
对高复杂决策跑"并行多实例 + 对抗式校验"提质

战略类问题（如项目二选址/合伙人筛选/内容选题），同时起多个实例走不同框架，再让一组实例去"挑另一组结论的毛病"。把你最强的模型用在"帮你想清楚要什么"，日常用快/省模型——这正是 Sonnet/Opus 的分工逻辑。

4一月
把项目二的重复流程封装成"斜杠命令/技能"复利·需搭建

对标内部市场团队"几分钟生成上百条广告变体"：把你高频的运营动作（线下合伙人话术批量生成、内容批量改写、数据看板→周报）固化成可复用命令/子代理流水线。"线下捞人"的素材生产可被规模化自动化。

5持续
建立"验收闸门"与刻意手感护栏

给自动化流程设 stop-hook 式的自动验收（跑完自检不过就回去重做）；同时保留对关键产出的人工审阅——并警惕监督悖论，别让自己丧失判断"危险地聪明"的方案的能力。

M心智（每次都先想）

  • 我是管理者，不是提问者——能否并行派发？
  • 这是 Sonnet 活（范围清晰）还是 Opus 活（帮我想清楚）？

  • 预计 <10 分钟能做完？→ 别折腾 AI 了。

P对话（写好一次性需求）

  • 用 <标签> 分开"指令 / 资料 / 示例 / 格式"。
  • 给 3 个好示例，而不是 20 条特例。
  • 说清为什么（约束动机）+ 用硬动词"去做"。
  • 复杂题加"深入思考"，别一步步规定死。

AAgentic（自动化流程）

  • 复杂任务先规划再执行，别想一把梭。
  • 评审让子代理互相挑刺，只修影响正确性的。
  • 设验收闸门：自检不过就回去重做。
  • 把高频流程固化成命令 / 子代理流水线。

C上下文（经营注意力）

  • 信号最高、数量最少——不是越长越好。
  • 长任务三件套：压缩 · 外部笔记 · 子代理隔离。
  • 大数据按需取用（存指针，动态加载）。
  • 一个会话一个目标，别"厨房水槽"。
